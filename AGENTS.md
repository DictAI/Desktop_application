# DictAI Frontend Agent Instructions

## Назначение и источники

Поддерживай Flutter desktop-приложение DictAI небольшими, проверяемыми изменениями.
Перед работой прочитай этот файл, `docs/ai/WORKFLOW.md`, `docs/ai/architecture.md`,
актуальную карточку задачи и её план, если они созданы для выбранного scope.
`docs/ai/README.ru.md` — инструкция команде.
Правила действуют и для документации; сама документация не доказывает работу кода.

## Обязательный процесс

1. Проверь `git status --short`, сохрани исходное состояние и посторонние изменения.
2. Изучи связанные исходники, тесты, конфигурацию, API-контракты и платформенный код.
   Проверяй выводы по текущим файлам, а не только по комментариям или истории чата.
3. Для большого запроса подготовь план и атомарные задачи по шаблонам `docs/ai/`.
   Планирование не разрешает менять реализацию.
4. Выполняй только явно выбранные пользователем задачи и область изменений.
   При работе по плану используй выбранные task ID; весь план выполняется только
   по явному поручению. Непринятые или невыбранные зависимости обозначай blocker,
   не реализуй их автоматически. Уже данное разрешение повторно не запрашивай.
5. Реализуй выбранный scope, выполни релевантные проверки, запиши их результаты.
6. Организуй независимый review и передай пользователю diff, findings и ограничения.
   Не выставляй `accepted` без явной приёмки пользователя.

Не расширяй scope самовольно. Изменение контракта, поведения авторизации,
хранения секретов, зависимостей, платформенных разрешений или выпуска должно
входить в уже разрешённый объём; иначе сначала объясни необходимость изменения.
Не создавай задачи по интеграции с backend без отдельного поручения.

## Учёт задач и координация

- Используй `docs/ai/PLAN_TEMPLATE.md`, `docs/ai/TASK_TEMPLATE.md` и
  `docs/ai/REVIEW_TEMPLATE.md`.
  Сохраняй YAML frontmatter, зависимости, acceptance criteria, Verification и Result.
- Правила ID, статусов и резервирования заданы в `docs/ai/WORKFLOW.md`.
  Координатор последовательно резервирует уникальные ID в `docs/ai/active-plan.md`
  до делегирования. Не переиспользуй отменённые или уже выданные ID.
- У каждой задачи должны быть ответственный `owner`, точный `scope` файлов и
  `planned_paths` для ещё не существующих файлов. Доступ на чтение не даёт
  права записи. Общие файлы и каталоги сначала разбей на непересекающиеся scopes.
- Параллельная запись допустима только при независимых задачах и непересекающихся
  областях файлов. Общие providers, router, тема и учётные документы требуют
  одного назначенного владельца записи. Реестр изменяет только координатор.
- При конфликте останови запись в пересекающиеся файлы, сообщи координатору и
  согласуй порядок. Не отменяй чужие изменения и не разрешай конфликт наугад.
- Отдельные ветки/worktrees могут изолировать работу, но не отменяют проверку
  пересечения scopes и итоговую интеграционную проверку.

## Flutter/Dart

- Сохраняй существующую структуру `lib/core`, `lib/features`, `lib/shared/providers`.
  Не добавляй новые архитектурные слои и генерацию кода без необходимости задачи.
- Riverpod: используй существующие Provider/StateNotifier-подходы; зависимости
  общих сервисов собираются в `lib/shared/providers/providers.dart`.
  Учитывай жизненный цикл notifier, timers, recorder и подписок; не создавай
  повторные сетевые запросы в `build`. Тесты изолируй через overrides/fakes.
- GoRouter: изучай `lib/core/router/app_router.dart` и
  `lib/core/router/auth_listenable.dart`.
  Сохраняй согласованность routes, ShellRoute и auth redirects. При изменении
  навигации проверяй вход, выход, истечение сессии и параметры маршрутов.
- Dio: используй общий `dioProvider` для backend API и существующие feature API.
  Не обходи AuthInterceptor. Учитывай JSON, multipart, bytes, таймауты и ошибки.
  Не добавляй секреты или чувствительные тела запросов в логи и документацию.
- DTO: сохраняй типы в соответствующем feature-каталоге, например
  `lib/features/auth/data/dto`, проверяй ключи JSON, nullability,
  даты и обязательность полей по связанному контракту. Не меняй wire format
  ради удобства UI и не подменяй отсутствующие данные выдуманными значениями.
  Сейчас сериализация ручная; наличие generator-зависимостей не означает их использование.

## API и платформенные границы

- Перед изменением API-клиента/DTO найди связанные вызовы, экраны и обработку ошибок.
  В этом репозитории нет локального OpenAPI. Если доступен backend-репозиторий,
  прочитай соответствующий HTTP-контракт и текущую реализацию в нём только для
  сверки. Если источник недоступен или расходится с клиентом, зафиксируй пробел;
  не выдумывай контракт и не изменяй соседний репозиторий без поручения.
- macOS: проверяй обе стороны MethodChannel, Swift-код, минимальную версию ОС,
  Info.plist и DebugProfile/Release entitlements. Изменения разрешений, подписи
  и способов захвата аудио не должны попадать в задачу незаметно.
- Linux: учитывай CMake/GTK, `pactl`, `parec`, `ffmpeg`, открытие/сохранение файлов
  и завершение внешних процессов. Не объявляй Linux проверенным после macOS-run.
- Изменение общего Dart-кода может затронуть обе платформы. Различай unit-проверку,
  platform build и ручной smoke. Не редактируй generated plugin registrants вручную.

## Проверки и доказательства

Матрица команд и требования к окружению описаны в `docs/ai/WORKFLOW.md`.
Начинай с самых узких релевантных проверок. Для изменённого Dart-кода обычно нужны
проверка формата, `flutter analyze` и осмысленные тесты затронутого поведения.
Для платформенных изменений добавь соответствующую сборку/smoke, если среда доступна.
Для документации достаточно проверки ссылок, согласованности и полного diff;
не запускай сборку или генерацию, не относящиеся к изменению.

В Verification запиши команду, cwd, окружение, PASS/FAIL/SKIP/NOT RUN и причину.
В Result запиши изменённые файлы, подтверждённый результат, findings и риски.
Не считай чтение исходников тестом. Пустой тест, skip и отсутствие окружения
не являются успешной проверкой. Не обновляй SDK/lock-файл для обхода проверки
без разрешения на такое изменение. Не сохраняй секреты из вывода команд.

## Независимый review

Полный review после реализации, включая организационную документацию, выполняет
отдельный агент/субагент, не писавший проверяемые изменения. Самопроверка автора
дополняет его, но не заменяет. Reviewer не меняет исходники, тесты, конфигурацию,
задачи и планы; может записать только заранее назначенный review-отчёт либо
передать findings координатору для дословной фиксации с указанием автора.

Проверяющий указывает task ID или явно заданный scope без задачи, базу/diff,
priority, файл, строку, impact, evidence, recommendation и ограничения проверки.
Не включай другой незапрошенный scope. Исправления findings выполняет implementer
в разрешённом пользователем объёме; требуемые текущим поручением исправления
согласованности не нуждаются в повторном разрешении. Остальные findings передай
на выбор. Отложенное замечание не помечай исправленным. Если независимый reviewer
недоступен, явно оставь review незавершённым, не подменяй его самопроверкой.

## Git и сохранность

- Не выполняй commit, push, merge, release или переписывание истории без явного
  разрешения пользователя на соответствующее действие. Приёмка задачи сама по
  себе не разрешает публикацию. Не удаляй данные и чужую работу.
- Не используй reset/clean/checkout для удаления посторонних изменений.
  Проверяй исходное состояние, итоговый diff и новые untracked-файлы.
- Новую ветку при необходимости называй `codex/<task-id>-<short-name>`, если
  пользователь не указал другое. Создание ветки не разрешает commit/push/merge.
- Держи относящиеся к реализации task/review-записи в том же предлагаемом diff.
  Не коммить секреты, токены, записи встреч, локальные caches и build artifacts.
