# Работа с Codex во frontend DictAI

Эта инструкция описывает процесс разработки Flutter/Dart-приложения.
Правила для агентов находятся в [AGENTS.md](../../AGENTS.md), подробный процесс —
в [WORKFLOW.md](WORKFLOW.md), карта существующего приложения —
в [architecture.md](architecture.md). [active-plan.md](active-plan.md) содержит
текущий выбор задач и реестр ID. История чата не заменяет эти файлы.

## Создать план

Для большой работы отправьте агенту:

```text
Изучи проект и подготовь план для задачи: <желаемый результат>.
Используй docs/ai/PLAN_TEMPLATE.md и docs/ai/TASK_TEMPLATE.md.
Через координатора зарезервируй уникальные FE ID в active-plan.md.
Укажи зависимости, точные файлы, критерии готовности, риски и проверки.
Создай только план и draft-задачи. Функциональный код пока не изменяй.
```

Проверьте, что каждая задача даёт один наблюдаемый результат, её зависимости
понятны, файлы перечислены, а результат можно проверить. Создание плана не
запускает реализацию. Начальных продуктовых или backend integration задач эта
система не содержит.

## Выбрать задачу и поручить реализацию

Следующие ID приведены только как примеры будущих карточек, сейчас их нет:

```text
Выполни TASK-FE-001.01 из PLAN-FE-001.
Реестр и карточка определяют scope. Остальные задачи не выполняй.
Проверь принятые зависимости, обнови статус и Result, запиши проверки.
После реализации проведи независимый review.
```

Чтобы выполнить весь существующий план, укажите его ID и это разрешение явно.
Непринятые зависимости и неразрешённые изменения контракта не выполняются молча.
Уже выбранную задачу повторно согласовывать не нужно.

## Запустить проверку

```text
Проверь выбранную задачу по разделу Verification и матрице WORKFLOW.md.
Запиши точные команды, cwd, окружение, результаты и ограничения в карточку.
Не изменяй реализацию: ошибки передай отдельным списком.
```

Для Dart обычно проверяются формат, analyzer и тесты затронутого поведения.
Для записи/файлов/MethodChannel важны отдельные platform smoke-проверки.
Для документации проверяются ссылки, согласованность и diff; Flutter build не нужен.
Пустой test-файл и SKIP не являются PASS. Требования SDK и известные ограничения
указаны в architecture.md; их исправление не выполняется автоматически.

## Провести независимый review

```text
Назначь отдельного reviewer, который не писал реализацию TASK-FE-001.01.
Проведи read-only review выбранного diff, критериев и результатов проверок.
Зарезервируй review ID и сохрани findings в docs/ai/reviews/ по шаблону.
Не исправляй реализацию. Укажи priority, файл, строку, impact и рекомендацию.
```

Read-only означает запрет изменений проверяемых файлов. Reviewer может записать
только назначенный отчёт; иначе передаёт текст координатору. Самопроверка автора
не считается независимым review. Пользователь выбирает исправления, выходящие
за уже разрешённые критерии текущей задачи; deferred findings сохраняются явно.

## Принять результат

После просмотра diff, проверок и review можно поручить:

```text
Принимаю TASK-FE-001.01 в зафиксированном scope и с указанными ограничениями.
Обнови status на accepted и запиши основание приёмки.
Commit, push, merge и release не выполняй.
```

`implemented` означает наличие реализации, `verified` — подтверждённые проверки,
`accepted` — явную приёмку пользователем. Приёмка может сохранять явно принятые
ограничения и не означает публикацию или проверку другой платформы.

## Совместная работа

Назначьте одного координатора для active-plan.md, выдачи ID и общих файлов.
Перед параллельной работой он фиксирует owner и непересекающиеся scopes.
Нельзя одновременно менять общий router/providers/тему или учётные файлы без
последовательной передачи владения. Reviewer не является вторым implementer.
Подробные правила и восстановление после конфликта находятся в WORKFLOW.md.
