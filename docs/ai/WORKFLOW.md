# Frontend AI Development Workflow

## Источники и роли

Основные ограничения задаёт [AGENTS.md](../../AGENTS.md). Текущая область работы
определяется поручением пользователя и карточками в [tasks/](tasks/).
Frontmatter конкретной задачи и последние явные решения имеют приоритет над
историческим текстом плана. [active-plan.md](active-plan.md) — краткий указатель
и реестр; при изменении статуса координатор синхронизирует карточку и таблицу плана.
Старую историю не следует выдавать за текущее разрешение.

| Роль | Ответственность и право записи |
|---|---|
| coordinator | Выдача ID, active-plan, общие записи, назначение scopes и интеграционный diff |
| planner | Исследование, план, draft-карточки; без функционального кода |
| implementer | Выбранный scope реализации, тесты и собственная task-карточка |
| verifier | Проверки и evidence; без изменения реализации, если это не поручено |
| reviewer | Независимая проверка; только назначенный review-файл или текст координатору |

Coordinator/planner/implementer/verifier могут быть режимами основного агента.
Reviewer должен быть другим агентом/субагентом, не писавшим проверяемый diff.
Согласованный write scope нужен и для документов, не только для исходников.

## ID и файлы

Используется frontend-префикс FE; номера в примерах ниже — будущие, не выданные ID:

- `PLAN-FE-001` → будущий `plans/PLAN-FE-001.md`.
- `TASK-FE-001.01` → будущий `tasks/TASK-FE-001.01.md`.
- `REVIEW-FE-001.01-01` → будущий `reviews/REVIEW-FE-001.01-01.md`.
  Последний номер — отдельный независимый проход review.

Точки и padding являются частью канонического ID. Числа могут расти дальше
трёх/двух цифр. Номера не переиспользуются после отмены. Один review может
перечислять несколько `task_ids`; ID связывается с первой проверяемой задачей.
Для bootstrap без task допустим отдельный `REVIEW-FE-SETUP-01`, с пустым
`task_ids` и явно указанным scope; это не продуктовая задача.

До создания файлов координатор последовательно:

1. Сверяет active-plan.md и все существующие планы/задачи/review, включая
   согласованные параллельные ветки и worktrees. Учитывает выданные, но ещё
   не закоммиченные ID; Git main сам по себе не является полным реестром.
2. Выдаёт следующий свободный ID и добавляет строку `reserved` в реестр.
   Это состояние резерва ID, а не статус задачи.
3. Указывает owner и путь будущего файла, только затем делегирует создание.
4. После создания меняет состояние резерва на `created`; отменённый резерв
   помечает `retired`. ID никогда не выдаётся повторно.

В разных checkout реестр сам не синхронизируется: до делегирования координатор
передаёт выданные ID всем исполнителям. Без общего координатора не выбирай
номер самостоятельно для параллельной записи. При коллизии останови публикацию
конфликтующей карточки, согласуй новый ID и обнови все ссылки, сохранив историю.

## Планирование и выбор

Исследуй исходники и ограничения, затем заполни [PLAN_TEMPLATE.md](PLAN_TEMPLATE.md)
и [TASK_TEMPLATE.md](TASK_TEMPLATE.md). Одна задача — один наблюдаемый результат.
Укажи `depends_on`, owner, scope, ещё не существующие `planned_paths`, критерии,
проверки и исключённый scope. Дай план пользователю для выбора ID.

`ready` означает готовность к выбору, но не разрешает реализацию. Перед стартом
проверь явный выбор задачи и `accepted` у обязательных зависимостей. Не выполняй
невыбранные зависимости автоматически. Существенные изменения требований
сначала согласуются в пределах поручения, затем фиксируются в decisions.md.

## Статусы задачи

```text
draft -> ready -> in_progress -> implemented -> verified -> review -> accepted
review -> changes_requested -> in_progress
любое незавершённое состояние -> blocked -> предыдущее допустимое состояние
незавершённая задача -> cancelled по решению пользователя
```

| Статус | Условие |
|---|---|
| draft | Scope, критерии, решения или зависимости ещё не готовы |
| ready | Карточка определена, обязательные зависимости приняты; ожидает выбора |
| in_progress | Задача выбрана, owner и write scope назначены, работа начата |
| implemented | Реализация есть; проверки ещё неполные или не прошли |
| verified | Все обязательные для выбранного scope проверки подтверждены evidence |
| review | Diff передан на независимый review; Result сохраняет точный статус проверок |
| changes_requested | Пользователь выбрал исправления по review |
| accepted | Пользователь явно принял конкретный результат и известные ограничения |
| blocked | Без внешнего решения/окружения/принятой зависимости продолжить нельзя; причина записана |
| cancelled | Пользователь отменил задачу; ID и история сохранены |

Review можно провести и до полной verification: тогда переход из implemented
в review допустим, но карточка явно перечисляет непрошедшие/незапущенные проверки
и не заявляет verified. Такой review не устраняет blocker. Приёмка с исключениями
требует явного решения пользователя; агент не закрывает критерии за него.
После новых изменений прежнее evidence оценивается заново, устаревший PASS
нельзя переносить на новый diff без основания.

## Параллельная работа

- Координатор записывает owner и активный scope в active-plan.md; карточка
  перечисляет конкретные файлы. Новые файлы одновременно указываются в
  `scope` и `planned_paths`. Чтение остальных файлов разрешено.
- Общий каталог не означает независимые файлы: перед стартом разверни scope
  до конкретных путей. Не назначай перекрывающиеся write scopes параллельно.
- Только координатор меняет реестр, общую таблицу плана и decisions.md.
  Исполнитель обновляет собственную карточку, сообщает статус координатору.
- Router, providers, тема, зависимости и платформенная конфигурация — частые
  точки пересечения. Назначай одного writer либо последовательные задачи.
- Worktree/ветка изолируют checkout, но общая правка всё равно требует
  согласования и проверки объединённого результата. Не делай merge без поручения.
- При неожиданном чужом diff останови запись в спорные файлы. Сохрани его,
  сообщи координатору и передай владение явно; не применяй reset/clean.
- Reviewer не исправляет diff. Его write scope — только назначенный отчёт;
  если выбран полностью read-only режим, отчёт сохраняет координатор с атрибуцией.

## Verification matrix

Команды выполняются из корня frontend, если не указан другой cwd. Это матрица
выбора проверок, а не требование запускать всё после каждого изменения.

| Изменение | Проверки |
|---|---|
| Только документация | Ссылки/пути, примеры ID, согласованность статусов/границ, whitespace и полный diff новых файлов |
| Dart UI/state | `dart format --output=none --set-exit-if-changed lib test`, `flutter analyze`, targeted unit/widget tests; при необходимости `flutter test` |
| API/DTO | Контракт, JSON fixtures, null/error/401, multipart/bytes и соответствующие тесты; реальные записи в API только в разрешённой тестовой среде |
| Навигация/auth | Redirects, login/logout/401, route parameters, состояние после смены сессии |
| Запись/загрузка/файлы | Permissions, start/pause/stop/error, cleanup, отсутствие повторных запросов, нужные unit/platform smoke |
| macOS | При доступном окружении `flutter build macos --debug`, smoke нужного MethodChannel и разрешений |
| Linux | На Linux с нужными пакетами `flutter build linux --debug`, smoke аудио/процессов/файлов |

Для targeted tests указывай реальный существующий файл. Новые тесты — будущие
файлы из `planned_paths`, пока они не созданы. Не используй пустой текущий
`test/widget_test.dart` как доказательство проверки приложения.

Перед Flutter-командами сравни SDK и lock-файл, проверь наличие зависимостей.
`flutter pub get` допустим для выбранной реализации при необходимости, но
результат и возможный diff lock-файла требуют проверки; обновление зависимостей
или SDK не входит в задачу автоматически. `--no-pub` применим только к уже
подготовленному окружению. Сборка macOS на Linux и Linux на macOS не считаются
выполненными. Не запускай генерацию Riverpod только потому, что пакет объявлен.

В карточке фиксируй: команду, cwd, SDK/ОС при значимости, ожидаемое и фактическое
поведение, PASS/FAIL/SKIP/NOT RUN, причину и остаточный риск. Отсутствующая
проверка не равна PASS. Для документации запиши Flutter-проверки как NOT RUN,
если они не относятся к scope; это само по себе не blocker документации.

`git diff --check` и `git diff` не показывают содержимое untracked-файлов.
Новые файлы отдельно проверяй чтением и `git diff --no-index /dev/null <file>`
(код 1 у обычного no-index diff означает наличие различий). Не делай staging
только ради просмотра. Проверяй `git status --short --untracked-files=all`.

## Review, приёмка и Git

Используй [REVIEW_TEMPLATE.md](REVIEW_TEMPLATE.md). Сохрани независимую личность
reviewer, базу и точный diff, проверенные критерии, findings и пределы проверки.
Отсутствие findings не доказывает невыполненные runtime checks. После выбранных
исправлений выполни нужные повторные проверки и delta review. Пользователь
принимает результат; agent не присваивает accepted сам.

Commit/push/merge/release требуют отдельного разрешения на действие.
Резервирование ID, готовый review и accepted task такого разрешения не дают.
Сохраняй посторонние изменения и включай относящиеся task/review records
в предлагаемый diff. Не переписывай историю и не удаляй локальную работу.
